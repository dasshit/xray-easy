# План тестирования backend

## Как считать покрытие

Из корня репозитория выполнить `bash scripts/backend-coverage.sh`. Скрипт запускает все Go-тесты заново, сохраняет `coverage.out` и печатает покрытие операторов по пакетам и в целом. Для просмотра функций или подсвеченного исходного кода:

```sh
go tool cover -func=coverage.out
go tool cover -html=coverage.out
```

Рабочая метрика — взвешенное по операторам покрытие рукописного Go-кода. Сгенерированные `*.pb.go` включены в обычный результат Go, но исключены из рабочей метрики. Вложенный модуль `third_party/go-qrcode` не входит в `./...`. Это покрытие тестами внутри пакетов; внешние контейнерные тесты и ручные проверки оцениваются отдельно. Процент операторов не показывает полноту проверки ветвей и корректность утверждений в тестах.

Сейчас есть 11 тестовых функций в пяти пакетах. Они проверяют:

- `internal/domain`: базовые переходы жизненного цикла устройства и часть валидации имени, fingerprint, публичного адреса и REALITY target.
- `internal/diagnostics`: маскирование нескольких видов секретов и ограничение размера буфера логов.
- `internal/store`: атомарность совместного изменения настроек и состояний устройств на настоящей временной SQLite базе. Это компонентный тест, а не изолированный unit-тест.
- `internal/xray`: сохранение учетных данных при преобразовании доменных структур, часть проверки публичного адреса, синхронизацию списка активных пользователей и REALITY short IDs при генерации server config, наличие поля `minClientVer`.
- `cmd/xray-easy`: fingerprint набора устройств при изменении состава и состояния, независимость от порядка строк БД.

На стартовой базе не было тестов HTTP API, supervisor, auth/TOTP/secret пакетов, backup/restore, статистики или gRPC-обращений к Xray.

Добавлены проверки RFC 6238, нормализации recovery-кодов, отказов на поврежденном зашифрованном envelope и границ валидации. `go test -race ./...` проходит.

### Результат этапа 2

Добавлены сценарии миграции и инициализации SQLite, сессий, TOTP и одноразовых recovery-кодов, устройств, трафика, аудита и операций apply; создание, проверка, список, ротация retention и восстановление backup; эксклюзивность и отмена maintenance lock. Покрытие целевых пакетов: `internal/store` — 83,2%, `internal/backup` — 84,1%, `internal/maintenance` — 83,3%. Общее покрытие рукописного Go-кода — **707 / 2836 операторов (24,9%)**.

### Результат этапа 3

Покрыты связи между VLESS URI и JSON экспортом, правила генерации серверной конфигурации и REALITY short IDs, формат UUID/X25519/short ID. Для HandlerService и StatsService добавлены тестовые gRPC-серверы поверх `bufconn`: проверяются сериализация Add/Remove user, выбор inbound, статистика, восстановление соединения и ошибка `Unimplemented` для старого StatsService. ### Результат этапа 4

Добавлены тесты `internal/stats` (100%) и `internal/supervisor` (92,3%), а также тесты жизненного цикла дочернего Xray-процесса, HTTP HMAC-аутентификации, защиты от replay, ограничения размера тела, SSRF-проверок target/SNI, redaction и healthcheck в `cmd/xray-supervisor` (81,6%). ## Порядок работы

Каждый этап заканчивается обновлённым отчетом `scripts/backend-coverage.sh`, проверкой `go test -race ./...` и отдельным коммитом с тестами и необходимыми небольшими изменениями для тестируемости. Тесты должны проверять наблюдаемое поведение, включая отказ и восстановление после сбоя, а не повторять шаги реализации.

### 1. Учетные данные и секреты

Покрыть `internal/auth`, `internal/totp`, `internal/secret`, оставшиеся ветви `internal/domain` и `internal/diagnostics`. Проверить пароль и recovery-коды, известные TOTP-векторы и временное окно, неверный/повторный код, round trip шифрования, неверные ключ и purpose, повреждённый envelope. В домене проверить все разрешённые и запрещённые переходы состояния устройства и граничные значения настроек. Для времени использовать фиксированные значения, для сравнения криптографии — внешние тестовые векторы.

### 2. Постоянное состояние и резервные копии

Покрыть `internal/store`, `internal/backup`, `internal/maintenance`. Использовать временную SQLite базу и каталоги: повторный запуск миграций, однократную инициализацию, сессии и их истечение/сброс, одноразовое расходование recovery-кода, CRUD и состояния устройств, snapshots трафика, операции apply и audit. Для backup проверить создание и восстановление, целостность manifest/HMAC, подмену файлов и неверный master key, очистку после ошибки, права файлов, маскирование active config и правило хранения последних 10 копий. Для maintenance lock проверить конкурирующее получение и отмену контекста.

### 3. Генерация конфигурации и адаптеры Xray

Довести `internal/xray`: профиль VLESS URI и клиентский JSON должны содержать одинаковые UUID, public key, short ID, SNI, fingerprint, flow и порт; проверить escape имени, невалидные настройки, отозванный профиль, пустой список клиентов и стабильный порядок конфигурации. Зафиксировать совместимость полей `password`/`publicKey` и `minClientVer` тестами на контракт. Для `internal/xrayapi` поднять локальный gRPC-сервер в тесте: HandlerService add/remove/list и обработка ошибок, StatsService `GetUsersStats`, отсутствие метода на старой версии Xray, сброс соединения и повторное подключение. Сгенерированные protobuf-файлы отдельно не тестировать.

### 4. Управление процессом и статистика

Покрыть `cmd/xray-supervisor`, `internal/supervisor`, `internal/stats`. Через `httptest` проверить HMAC подпись, nonce replay/TTL, ограничение тела запроса, разрешённые пути, SSRF-защиту probe, маскирование логов и HTTP-контракт. Через тестовый исполняемый файл проверить validate/apply, быстрый выход дочернего процесса и rollback к `active.json`, не запуская настоящий Xray. Для статистики проверить накопление трафика после сброса счетчиков/рестарта Xray, отсутствие отрицательных дельт, online-window, восстановление snapshots из SQLite, ошибки polling и подписки. Ввести часы и внешние зависимости через интерфейсы там, где это нужно для детерминированных тестов.

### 5. Control plane и CLI

Разбить тестирование `cmd/xray-easy` по сценариям через `httptest` и временную SQLite базу с подменой supervisor/Xray API: первичная настройка, пароль и TOTP/recovery login, cookie и срок сессии, logout-all, доступ к защищённым маршрутам; создание, включение, выключение, отзыв, экспорт профиля; preview/confirm/apply настроек, ротация ключа, автоматический backup, атомарность и rollback при ошибке на каждом внешнем шаге; reconciler и SSE. Отдельно проверить `backup`, `restore`, `admin` CLI и ошибки конфигурации окружения. Большой `main.go` разделить по прикладным сценариям и добавить узкие интерфейсы зависимостей только по мере написания тестов, сохраняя HTTP-контракт.

### 6. Завершение покрытия и регрессионный барьер

Покрыть оставшиеся ветви `internal/ui` и остальных пакетов, добавить table-driven негативные и граничные случаи. В CI запускать быстрый Go набор, `go test -race ./...` и скрипт покрытия. По мере этапов поднимать минимальный порог без регресса. Итоговый ориентир: не менее 90% операторов рукописного Go-кода, не менее 80% в каждом пакете и проверенные успешные, ошибочные и rollback-пути каждой критичной операции. Исключения для недостижимых защитных ветвей или процесса запуска документировать поименно; не добавлять тесты только ради процента.

Отдельный контейнерный contract/E2E набор с закрепленной версией Xray проверит действительную загрузку конфигурации, работу gRPC и подключение профиля. Он не заменяет описанные unit/component тесты и не включается в их порог покрытия.
